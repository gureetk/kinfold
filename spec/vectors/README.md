# Test vectors for protocol v0

`kinfold-v0.json` is released under [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/). It is generated by `reference/python/gen_vectors.py` (deterministic: the same bytes every run) and checked by `reference/python/check_vectors.py`.

```sh
cd reference/python
python3 check_vectors.py ../../spec/vectors/kinfold-v0.json
# regenerating needs the RFC 9180 vectors file from github.com/cfrg/draft-irtf-cfrg-hpke
python3 gen_vectors.py ../../spec/vectors/kinfold-v0.json path/to/test-vectors.json
```

## Conventions

- Byte strings are lowercase hex. Links, URLs, names, digit codes and JSON text are plain strings; decoded payloads are JSON objects.
- Times are milliseconds since the Unix epoch, UTC. The scenario starts at `1793635200000` (2026-11-02T16:00:00Z).
- Every key, secret and nonce was derived as `SHA-256("kinfold-test-vector/" ‖ tag)`. They are public: never use them outside tests.
- X25519 private keys (`sk`) are raw 32-byte scalars; Ed25519 private keys (`*_seed`) are 32-byte seeds. WebCrypto imports both through JWK (`d` = base64url of the bytes).
- Reason codes are the strings in PROTOCOL.md §16.5.

## Groups

### `primitives`

`H`, `kdf` and `sign` each give a full label (`kinfold/v0/test`), inputs and the expected output. Ed25519 is deterministic, so `sig` must match exactly. `b64u` pairs bytes with their unpadded base64url text.

### `hpke_rfc9180`

The RFC 9180 test case for mode 0 with KEM 0x0020, KDF 0x0001 and AEAD 0x0002, and its first two encryptions (the nonce for encryption *i* is `base_nonce XOR i`). Implementations that can't fix the ephemeral key check `open` with `skRm`, `enc` and `info` only.

### `identities`

Four people — `jordan`, `alex`, `maya`, `sam` — each with `ik_seed`, `ik_pub`, `account_id` and `devices`. A device has `label` (`person/device`), `kind`, `dsk_seed`, `dsk_pub`, `device_id`, `cert` (a DeviceCert), `deks` (each `{sk, pub, key_id}`, oldest first) and `bundles` (`bundles[i]` publishes `deks[i]`). `maya/phone` rotates its key at log entry 6; `jordan/tablet` is added at entry 5 and removed at entry 7; `jordan/web` and `sam/phone` never join the main log.

### `log`

- `circle_id`, `epoch_secrets` (`{"0": …, "1": …, "2": …}`), `final_seq` (13).
- `entries`: the main log, in order. Each has `seq`, `author` (device label), `description`, `raw`, `hash`, `result` and `reason` (client outcome), `public_result` and `public_reason` (what a server computes), and `state_after`. Optional: `details_plaintext` (the decrypted details), `invite_secret` and `invite_id` (ADD_MEMBER), `new_epoch`, `new_epoch_secret` and `wrap_ikm` (entries that start an epoch; `wrap_ikm` maps each recipient device ID to the HPKE `ikmE` used for its wrap).
- `cases`: each starts from the main log replayed through `base_seq` (inclusive; `-1` means an empty log) with all epoch secrets, then applies its `entries` in order. Entries have the same fields as above; fatal entries have no `state_after` and leave the state unchanged. A case's `state_after` is the state after its last entry when that entry isn't fatal; `new_epoch_secrets` gives secrets for epochs the case starts.

**State JSON.** `{circle_id, seq, head, epoch, members, name, flags}`. `members` is sorted by `account_id`; each is `{account_id, admin, devices, role, teen_until, guardians, rules, pauses}` with `devices` sorted by `device_id` as `{device_id, kind, key_id}`, `rules` null for adults or `{pause_mode, approx_mode, speed_alert_kmh, phone_use_alerts, history_days, silence_alert_min, schedule: [{kind, days, start_min, end_min}]}`, and `pauses` sorted by `id` as `{id, kind, start, end}`. `flags` lists `{seq, reason}` for rejected and flagged entries. The **public state** a server keeps is the same object without `name`, `flags`, `role`, `teen_until`, `guardians`, `rules` and `pauses`.

### `envelopes`

- `receiver_now`: the clock (ms) that receivers and servers use for every envelope check here.
- `valid`: `sender`, `kind`, `seq`, `sent_at`, `ttl_s`, `log_head`, `message_secret`, `wrap_ikm`, `payload_bytes` (the exact JSON bytes before padding), `padded_length`, `raw`, and `recipients` — each `{device, device_id, keys, payload}`, where `keys` maps key IDs to the X25519 private keys the device holds and `payload` is the expected JSON object. The receiver's log is the main log through `log_seq`.
- `invalid`: `raw`, `receiver`, `receiver_device_id`, `receiver_keys`, `log_seq` and the expected `error`. Faults deeper than the signature (bad wrap, wrong message secret, bad padding, bad JSON, unsorted wraps) are in envelopes the sender signed correctly.
- `replay`: one receiver processes `sequence` in order with a shared replay set; expect `results`.
- `server_rejects`: envelopes a server must refuse with `server_error` (PROTOCOL.md §7.5) but that the `receiver` can still open to `payload`. The `invalid` envelopes are refused by servers too when their `error` is one of the codes in §7.5's checks (steps 1–10).

### Others

- `padding.valid`: `payload_length` copies of `payload_byte`, padded to `padded_length`, whose SHA-256 is `padded_sha256`. `padding.invalid`: inputs `Unpad` must reject.
- `approx`: input `lat`, `lon` and the snapped `approx_lat`, `approx_lon` (PROTOCOL.md §8.3; note the negative and boundary inputs).
- `safety_codes`: the two identity keys, each person's 15-digit `half`, the 30-digit `code` (the same whichever key is "a") and the `qr` link.
- `invite`: Maya's invite (`invite`, `fields`, both links), `invite_id`, `join_key`, and her `join_request` (`message` is the posted bytes; `nonce`, `cert`, `bundle`, `consent` and `name` are inside it). Log entry `log_entry_seq` (2) carries the same `invite_id` and consent signature.
- `device_link.from_existing`: Jordan's phone shows `link` to add the tablet; `request` (with `request_plaintext`, `request_nonce`), the 6-digit `code`, and `response` (HPKE `response_ikm`, JSON `response_payload`), which the tablet opens with `new_device_dek_sk`. `device_link.from_new`: a browser shows `link` (direction 2), the phone posts `offer`, then the same request, code and response fields as above (no `ik` for a web device). The matching `ADD_DEVICE` entries aren't part of the main log.
- `share_link`: `server_url`, `secret`, `link_id`, `share_key`, `url`, `payload_bytes` (the JSON before padding), and one `update` with its `payload`.
- `auth`: the server's key and signed `server_info` document, a login `challenge` with `challenge_sig`, and the device's `device_sig`.
