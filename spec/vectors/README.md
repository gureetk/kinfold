# Test vectors for protocol v0

`kinfold-v0.json` matches [PROTOCOL.md](../PROTOCOL.md) draft 0.3 and is released under [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/). It is generated by `reference/python/gen_vectors.py` (deterministic: the same bytes every run) and checked by three implementations:

```sh
python3 reference/python/check_vectors.py spec/vectors/kinfold-v0.json
node reference/js/verify.mjs spec/vectors/kinfold-v0.json
(cd reference/go && go run . ../../spec/vectors/kinfold-v0.json)      # what a server enforces
# regenerating needs the RFC 9180 vectors file from github.com/cfrg/draft-irtf-cfrg-hpke
python3 reference/python/gen_vectors.py spec/vectors/kinfold-v0.json path/to/test-vectors.json
```

The file is about 1.3 MB. Most of that is a handful of vectors that test size limits.

## Conventions

- Byte strings are lowercase hex. Codes, links, URLs, names, digit codes and JSON text are plain strings; decoded payloads are JSON objects.
- Times are milliseconds since the Unix epoch, UTC. The scenario starts at `1793635200000` (2026-11-02T16:00:00Z). Two vectors sit at the top of the u64 range, where a time limit written as a sum wraps around: the log case `accepted_bundle_at_end_of_time` and the envelope `bad_time_end_of_time` (PROTOCOL.md Appendix C).
- Every key, secret and nonce was derived as `SHA-256("kinfold-test-vector/" ‖ tag)`. They are public: never use them outside tests.
- X25519 private keys (`sk`) are raw 32-byte scalars; Ed25519 private keys (`*_seed`) are 32-byte seeds. WebCrypto imports both through JWK (`d` = base64url of the bytes).
- Reason codes are the strings in PROTOCOL.md §16.5.
- A vector's `name` is stable; its `description` says in a sentence what it shows.

## What a server must pass, and what a client must pass

A client passes everything. A server passes `primitives`, `hpke_rfc9180`, `ed25519`, `x25519`, `identities`, the log in public mode (`public_result`, `public_reason` and the public state), the `server_error` of every envelope, `server_repost`, `watch_grants`, building the `push` vectors and the relay signature, `setup`, `server_moves` and `auth`. Rebuilding a sealed object byte for byte needs a fixed HPKE ephemeral key (`ikm`, `wrap_ikm`, `response_ikm`), which many platforms can't inject; those checks are optional, and opening is not (§3.5).

## Groups

### `primitives`

`H`, `kdf` and `sign` each give a full label (`kinfold/v0/test`), inputs and the expected output. Ed25519 is deterministic, so `sig` must match exactly. `b64u` pairs bytes with their unpadded base64url text.

### `hpke_rfc9180`

The RFC 9180 test case for mode 0 with KEM 0x0020, KDF 0x0001 and AEAD 0x0002, and its first two encryptions (the nonce for encryption *i* is `base_nonce XOR i`). Implementations that can't fix the ephemeral key check `open` with `skRm`, `enc` and `info` only.

### `ed25519` and `x25519`

The edge cases of §3.3 and §3.5, where libraries disagree.

- `ed25519.signatures`: `pub`, `msg` (the exact bytes signed: no label is added), `sig`, and `valid`, the verdict every implementation MUST return. `without_byte_checks` is what the bare equation `[S]B = R + [k]A` gives when none of §3.3's three byte checks is made; where it differs from `valid`, the byte checks are what decide. `cofactored: true` marks the mixed-order cases, whose verdict would change in a verifier that multiplies by the cofactor or doesn't reduce `k` first. A library is fit to sit behind the byte checks only if it returns `valid` on every one of these.
- `ed25519.keys` and `x25519.keys`: `pub` and whether it is an `invalid` key in the sense of §3.3 or §3.5.

### `identities`

Five people: `jordan`, `alex`, `maya`, `sam`, `riley`. Each has `ik_seeds` and `ik_pubs` (every identity key the person has had, oldest first), `ik_seed` and `ik_pub` (the current one), `account_id` (from the *first* key, §4.2), `chain` (the identity chain: one 192-byte link per rotation, empty for most) and `devices`.

A device has `label` (`person/device`), `kind`, `dsk_seed`, `dsk_pub`, `device_id`, `cert` (a DeviceCert under the person's *current* identity key), `deks` (each `{sk, pub, key_id}`, oldest first) and `bundles` (`bundles[i]` publishes `deks[i]`). A recovery device has no keys and no bundles.

- `alex` rotates his identity key at log entry 19. Entries before that carry certificates under his first key, so a certificate found in the log can differ from `cert` here; it verifies under the key it names.
- `riley` rotated before joining anything. She appears in one case, which adds her with her chain.
- `jordan/tablet` is added at entry 5 and removed at entry 7. `jordan/web`, `jordan/ha` and `jordan/recovery` are added at entries 15 to 17. `jordan/phone2` is the phone a recovery case adds. `alex/tablet` is added at entry 20. `sam/phone` appears only in cases.

### `log`

- `circle_id`, `epoch_secrets` (`{"0": …, "1": …, "2": …}`), `base_seq` (13) and `final_seq` (20).
- `entries`: the main log, in order. Each has `seq`, `author` (device label), `description`, `raw`, `hash`, `result` and `reason` (the client's outcome), `public_result` and `public_reason` (what a server computes), and `state_after`. Optional: `details_plaintext` (the details, decrypted and unpadded); `invite_secret`, `invite_id`, `terms_salt`, `terms` and `terms_commit` (ADD_MEMBER); `new_epoch`, `new_epoch_secret` and `wrap_ikm` (entries that start an epoch; `wrap_ikm` maps each recipient device ID to the HPKE `ikmE` used for its wrap).
- `cases`: each starts from the main log replayed through `base_seq` — 13, 20, or `-1` for an empty log — with all epoch secrets, then applies its `entries` in order. Names begin with the outcome of the last entry (`fatal_`, `rejected_`, `accepted_`, `deferred_`); the `kind_` cases are one entry type each from a web, Home Assistant or recovery author. Entries have the same fields as above. A fatal entry has no `state_after` and leaves the state unchanged. Entries that only set a case up may omit `state_after`; the last entry always has one unless it is fatal. `new_epoch_secrets` gives secrets for epochs the case starts. A case with `withheld_epochs` is processed without those secrets, as a device that never received them would (§6.5); its entries can have the result `deferred`.
- `state_hash`: `state_bytes` and `state_hash` (§6.9) for the client state after entry `log_seq`.

Entries 0 to 13 are a circle of two adults and a teen, with policies, a removed device and two new epochs. Entries 14 to 20 turn on web and Home Assistant devices, link one of each, add a recovery device, let the browser rotate its own key, rotate Alex's identity key, and add a device under his new key.

**State JSON.** `{circle_id, seq, head, epoch, rekey_pending, options, used_invites, members, name, flags, private_unknown_from, state_hash}`.

- `used_invites` is sorted. `members` is sorted by `account_id`; each is `{account_id, ik_pub, admin, devices, role, teen_until, guardians, rules, pauses}`.
- `devices` is sorted by `device_id`, each `{device_id, kind, key_id}`; `key_id` is null for a recovery device.
- `rules` is null for adults, or `{pause_mode, approx_mode, speed_alert_kmh, phone_use_alerts, history_days, silence_alert_min, tz, schedule: [{kind, days, start_min, end_min}]}`. `pauses` is sorted by `id`, each `{id, kind, start, end}`.
- `flags` lists `{seq, reason}` for rejected and flagged entries.
- `private_unknown_from` is null unless a missing secret froze the private state; while it is frozen the private fields keep their last known values and `state_hash` is null.

The **public state** a server keeps is the same object without `name`, `flags`, `private_unknown_from`, `state_hash`, `role`, `teen_until`, `guardians`, `rules` and `pauses`.

### `envelopes`

- `receiver_now`: the clock (ms) that receivers and servers use for every envelope check here. The receiver's log is the main log through the vector's `log_seq` (13 or 20), with every epoch secret.
- `valid`: `sender`, `kind`, `seq`, `sent_at`, `ttl_s`, `log_head`, `message_secret`, `wrap_ikm`, `payload_bytes` (the exact JSON bytes before padding), `padded_length`, `raw`, `payload` (the JSON object every recipient must get) and `recipients`, each `{device, device_id, keys}`, where `keys` maps key IDs to the X25519 private keys that device holds. A server stores every one of them. Between them they carry every payload type of §8.2.
- `invalid`: `raw`, `receiver`, `receiver_device_id`, `receiver_keys`, the `error` the receiver must report, and `server_error`: what a server answers, or null when a server has no grounds to refuse and stores the envelope. Faults deeper than the signature (a bad wrap, a wrong message secret, bad padding, a payload outside the limits, a payload the sender may not send) are in envelopes the sender signed correctly.
- `replay`: one receiver processes `sequence` in order with a shared replay record; expect `results`.
- `server_repost`: one server processes `sequence` in order: the first post is `stored`, the same bytes again are a `duplicate` (a success), and different bytes under the same sender and `seq` are a `replay` (§7.5).
- `server_rejects`: envelopes a server must refuse with `server_error` but that the `receiver` can still open to `payload`.

### `padding`, `approx`, `safety_codes`

- `padding.valid`: `payload_length` copies of `payload_byte`, padded to the bucket `padded_length`, whose SHA-256 is `padded_sha256`. `padding.pad_to`: the same for `PadTo` with the fixed size `to` (512 for log details, 2,560 for pushes). `padding.invalid`: inputs `Unpad` must reject.
- `approx`: input `lat`, `lon` and the snapped `approx_lat`, `approx_lon` (§8.3; note the negative and boundary inputs).
- `safety_codes`: the two current identity keys, each person's 30-digit `half`, the 60-digit `code` in twelve groups (the same whichever key is "a") and the `qr` text.

### `invite`

Alex's invite for Maya: `invite` (the bytes), `code` (`KFI0…`), `link_base` and `link`, the parsed `fields`, the decoded `terms`, `invite_id`, `join_key`, `join_result_key` and `terms_commit`. `join_request` is what Maya posts (`message`), opened at the time `now`: `nonce`, `cert`, `chain`, `bundle`, `consent` and `name` are inside it. `join_result.added` and `.declined` are the two answers the inviter can post, each with `nonce`, `message`, `outcome` and `head`. Log entry `log_entry_seq` (2) carries the same `invite_id`, `terms_commit` and consent signature.

### `device_link`

Three complete exchanges: `from_existing` (Jordan's phone shows the code, his tablet scans it), `from_new` (a browser shows the code, the phone scans it and posts an `offer`) and `from_existing_rotated` (Alex's phone and tablet, after his identity key rotated, so the response carries a chain).

Each has `direction`, `link`, `code_text` (`KFL0…`), `secret`, `link_id`, `link_key`, `confirm`, the labels `existing_device` and `new_device`, `account_id` and `ik_pub`, and then the messages in the order of §10.2: `commit_message` (`commit_nonce`, plaintext `commit`), `nonce_message` (`nonce_nonce`, plaintext `r_old`), `request` (`request_nonce`, plaintext `r_new ‖ request_body`), the 6-digit `code`, and `response` (HPKE `response_ikm`, JSON `response_payload`), which the new device opens with `new_device_dek_sk`. `now` is the existing device's clock when it checks the request. The matching `ADD_DEVICE` entries are main-log entries 5, 15 and 20.

`refused` holds requests the existing device must refuse: `commit_message`, `r_old` and `request` for the given `secret`, `direction` and `account_id`.

### `recovery_kits`, `setup`, `server_moves`

- `recovery_kits`: for `owner`, the `kit` bytes and `code` (`KFR0…`) with their fields. Jordan's is the recovery device of log entry 17. Alex's was made after his rotation and carries his chain.
- `setup`: the `setup` bytes and `code` (`KFS0…`) with their fields.
- `server_moves`: each `move` with its fields and whether a client that trusts `old_key` at `old_url` follows it (`valid`).

### `share_link` and `auth`

- `share_link`: `server_url`, `secret`, `link_id`, `share_key`, `url`, `payload_bytes` (the JSON before padding), and one `update` with its `payload`.
- `auth`: the server's key and signed `server_info` document, a login `challenge` with `expires_at` and `challenge_sig`, and the device's `device_sig`.

### `watch_grants` and `push`

- `watch_grants`: `grants`, each a 131-byte `grant` and whether it is `valid` at the time `now` against the main log through `log_seq`. `fields` are the fields of the first grant, `issued_at` among them.
- `push.valid`: for `device`, the `push` (type, `sent_at`, `body`, signed with the server key `push.server_key`), the HPKE `ikm` and the 2,616-byte `sealed` form, opened at the device's trusted time `now` with `keys`. `push.invalid`: sealed pushes the device must drop. `push.relay`: a relay signature over `capability`, `sealed`, `sent_at` and `delivery`.

## Not in the file

- The avatar limit of §8.1 (43,700 bytes): a vector would add a quarter of a megabyte. Each checker tests both sides of it by hand, along with the other payload limits.
- `bad_time` for log entries: it depends on the server's clock (§6.7).
- Anything about the HTTP API.
